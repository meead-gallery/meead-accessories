# MEEAD ACCESSORIES — Web App (Front-end)

اپلیکیشن خرید و فروش ساچمه نقره برای فروشگاه MEEAD ACCESSORIES.
این پکیج، سورس کد کامل و قابل‌انتقال نسخه‌ی فعلی پروژه است.

## نسخه‌ی React و وابستگی‌ها

این پروژه اصالتاً داخل محیط **Claude Artifacts** نوشته و اجرا شده — محیطی که خودش React
(نسخه‌ی پایه، از طریق `import { useState, useEffect, ... } from "react"`) و مجموعه‌ای از
کتابخانه‌های از پیش نصب‌شده (از جمله `lucide-react@0.383.0` برای آیکون‌ها) را در اختیار
کد قرار می‌دهد؛ در آن محیط فایل `package.json` یا فرآیند نصب جداگانه‌ای وجود ندارد.

برای اینکه این zip به‌صورت یک پروژه‌ی مستقل و قابل‌اجرا (با `npm install` و `npm run dev`)
هم کار کند، یک اسکلت استاندارد **Vite + React** دورش ساخته شده با نسخه‌های زیر:

| بسته | نسخه | نقش |
|---|---|---|
| `react` | `^18.2.0` | کتابخانه‌ی اصلی — کد فقط از هوک‌های پایه (`useState`, `useEffect`, `useCallback`) استفاده می‌کند، پس با هر ۱۸.x سازگار است |
| `react-dom` | `^18.2.0` | رندر روی DOM |
| `lucide-react` | `0.383.0` | آیکون‌ها (همان نسخه‌ای که در Artifact استفاده شده) |
| `vite` + `@vitejs/plugin-react` | `^5.2.0` / `^4.2.1` | فقط برای اجرای مستقل خارج از Artifact — بخشی از منطق برنامه نیست |

هیچ کتابخانه‌ی دیگری (Redux، React Router، Tailwind و…) استفاده نشده؛ تمام استایل‌ها CSS خام
داخل خود `App.jsx` هستند و تمام routing با یک متغیر state ساده (`view`) مدیریت می‌شود.

## ساختار فایل‌ها

```
meead-project/
├── package.json              # وابستگی‌ها و اسکریپت‌های dev/build
├── vite.config.js            # تنظیمات Vite
├── index.html                # نقطه‌ی ورود HTML
├── README.md                 # همین فایل
├── TECHNICAL_ARCHITECTURE.md # گزارش فنی کامل معماری (لایه api، مدل داده، endpointهای لازم برای بک‌اند واقعی)
└── src/
    ├── main.jsx               # نصب و رندر <App /> روی #root
    ├── App.jsx                # *** کل اپلیکیشن — تمام کامپوننت‌ها، لایه‌ی api، استایل‌ها ***
    └── shims/
        └── windowStorageShim.js   # شبیه‌ساز window.storage با localStorage (فقط برای اجرای محلی)
```

### چرا همه‌چیز در یک فایل (`App.jsx`) است؟

پروژه از ابتدا به‌صورت یک Artifact تک‌فایلی ساخته شده. با این حال، **داخل همان یک فایل**،
معماری کاملاً لایه‌بندی‌شده است (این تفکیک منطقی، نه فیزیکی، است):

| بخش منطقی | خط تقریبی در `App.jsx` |
|---|---|
| Config پایه (محصولات، تنظیمات پیش‌فرض، وضعیت‌های سفارش) | ابتدای فایل |
| توابع کمکی خالص (فرمت قیمت/زمان، محاسبه ساعات بازار) | بعد از Config |
| `store` — تنها نقطه‌ی تماس با `window.storage` | قبل از `api` |
| `api` — لایه‌ی سرویس / تمام منطق تجاری | بخش اصلی وسط فایل |
| کامپوننت `App` — مدیریت state و routing بین صفحات | بعد از `api` |
| صفحات مشتری (Home, OrderForm, OrderSummary, BuyPayment, SellSubmitted, TrackOrder) | میانه‌ی فایل |
| پنل مدیریت (Admin + تب‌های Dashboard/Prices/Orders/Customers/Market/Settings/Log/Backup) | بعد از صفحات مشتری |
| `GlobalStyles` — تمام CSS پروژه | انتهای فایل |

جزئیات کامل هر بخش، امضای هر متد `api`، مدل داده‌ی دقیق سفارش‌ها/تنظیمات، و لیست
endpointهایی که برای تبدیل به بک‌اند واقعی لازم است، در فایل **`TECHNICAL_ARCHITECTURE.md`**
آمده است — همان گزارشی که پیش‌تر تحویل داده شد، بدون هیچ تغییری.

## نکته‌ی مهم درباره‌ی Storage

تابع `store` در `App.jsx` روی `window.storage` ساخته شده — یک API مخصوص محیط Claude
Artifacts، نه یک استاندارد وب. برای اینکه این zip بیرون از Artifact هم بالا بیاید،
فایل `src/shims/windowStorageShim.js` یک نسخه‌ی جایگزین با `localStorage` ساخته که
**فقط برای اجرای محلی/تست است** — تک‌کاربره است و معادل واقعی «shared storage» نیست.

برای اتصال به یک بک‌اند واقعی، طبق چیزی که در `TECHNICAL_ARCHITECTURE.md` توضیح داده شده،
فقط کافی است بدنه‌ی توابع داخل `api` (نه کامپوننت‌های UI) با فراخوانی `fetch()` به
endpointهای واقعی جایگزین شود.

## اجرای محلی

```bash
npm install
npm run dev
```

سپس آدرس نمایش داده‌شده در ترمینال (پیش‌فرض `http://localhost:5173`) را باز کنید.

رمز پیش‌فرض پنل مدیریت: `meead1404` (از داخل پنل، تب «تنظیمات»، قابل تغییر است).
